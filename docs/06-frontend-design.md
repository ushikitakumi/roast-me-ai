# 06. フロントエンド設計

> **v1 のスコープと、削った機能の理由は [README](./README.md) を参照。**

## 0. 前提: React / TypeScript / Next.js は未経験

**これが本章の設計を規定する最大の制約である。** バックエンドが本領であり、フロントは「動くものを最短で用意する」ことを優先する。

そのため v1 では**使う概念を意図的に絞る**。

| 使う | 使わない（【将来】） | 理由 |
|---|---|---|
| Next.js App Router（`page.tsx` と `layout.tsx` だけ） | Server Actions、複雑な RSC 境界 | 学ぶ概念を減らす |
| TanStack Query | 自前の `useEffect` + `setInterval` | **ポーリングを `refetchInterval` の 1行で書ける**。自前実装のクリーンアップ漏れは初心者が最も踏むバグ |
| `useState` | Zustand などの状態管理ライブラリ | v1 の UI 状態は画面ローカルで足りる |
| 素の `<form>` + Zod | React Hook Form | フォームが 2枚しかない |
| Tailwind CSS | shadcn/ui | 必要になってから足す |
| `<img>` / `<video>` | PixiJS / Live2D / WebGL | **動画生成が Live2D の役割を引き継いだ**（§5） |
| `openapi-typescript` の生成型 | 手書きの型定義 | **TypeScript 未経験でも型が保証される。手書きの型を 1つも書かずに済む** |

**`openapi-typescript` の採用は、この制約下でとくに効く。** バックエンドの OpenAPI から型が降ってくるので、フロントで型を考える場面がほぼ消える（[03 §5](./03-api-design.md)）。

1人用でも初回に一度表示する。

> **このアプリはあなたを煽ります。**

## 3. 段階表示とポーリング ★中核

**フロントエンドで最も設計が要る部分。** [02 §5](./02-architecture.md) のジョブ状態が、そのまま画面の状態になる。

### 3.1 表示の遷移

| ジョブ状態 | 画面 |
|---|---|
| （投稿直後） | 入力欄を無効化、「考えている…」 |
| `TEXT_DONE` | **煽り文を表示**（ここで刺さる）+ 待機画像 + 「音声を作っています」 |
| `AUDIO_DONE` | 煽り文 + **🔊 再生ボタン** + 「動画を作っています 0:42」 |
| `VIDEO_SUBMITTED` | 同上（経過時間だけ進む） |
| `VIDEO_DONE` | 煽り文 + **`<video>` に差し替え**（再生ボタン付き） |
| `DEGRADED` | そこまでの成果物 + 理由の一文（「今日はもう動画は出ない」等） |
| （3分経過） | ポーリング停止 + 「できたらタイムラインに出る」 |

### 3.2 実装

**ポーリングは TanStack Query の `refetchInterval` に任せる。** 自前の `setInterval` を書かない。

```ts
// features/roast/useRoastPolling.ts
export function useRoastPolling(roastId: string | null) {
  const startedAt = useRef(Date.now());

  return useQuery({
    queryKey: ['roast', roastId],
    queryFn: () => api.get(`/roasts/${roastId}`),
    enabled: roastId !== null,

    // サーバが指示した間隔で再取得する。
    // pollAfterMs が null（終端状態）なら false を返してポーリングを止める。
    refetchInterval: (query) => {
      const data = query.state.data;
      if (!data?.pollAfterMs) return false;

      // 3分で打ち切る（Q16 の (d)）。生成は続き、完成後はタイムラインに出る。
      if (Date.now() - startedAt.current > 3 * 60 * 1000) return false;

      return data.pollAfterMs;
    },
  });
}
```

**間隔をサーバが指示する設計にした理由**（[03 §3.2](./03-api-design.md)）:

- 段階ごとに適切な間隔が違う（音声は 2秒、映像は 3〜5秒）
- フロントに間隔のロジックを持たせない。**未経験の領域にロジックを置かない**
- 終端状態で `null` が返るので、**「いつ止めるか」の判断がフロントに要らない**

### 3.3 なぜ SSE / WebSocket にしないか

| 観点 | 判断 |
|---|---|
| 更新の粒度 | 段階が**3つしかない**。常時接続で得られる情報が増えない |
| 時間スケール | **数十秒**。2〜3秒のポーリングで体感差がない |
| 実装コスト | ポーリング +1h に対し SSE +3〜4h / WebSocket +6h |
| 運用リスク | **Vercel の関数タイムアウト**と **Railway 越しの長時間接続**で詰まりやすい。未経験で踏む地雷としては割に合わない |

> README には「更新が3段階・数十秒スケールのため、常時接続の維持コストに見合わないと判断しポーリングを選択」と書く。**知らなくて選ばなかったのではなく、比較して選ばなかったことが伝わる。**

## 4. メディアの再生

### 4.1 自動再生しない（安全要件）

**`<video>` も `<audio>` も自動再生しない。** ユーザーが再生ボタンを押して初めて音が出る。

- ブラウザの自動再生ポリシー上、音声付きの自動再生はどのみちブロックされる
- **それ以上に安全上の理由がある。** テキストは目を逸らせるが、勝手に再生される動画は逸らせない。**再生の主導権をユーザーに残すことが、映像を採用したことで新たに必要になった安全設計**（[05 §5.5](./05-llm-design.md)）

```tsx
<video
  src={roast.videoUrl}
  poster={persona.avatarImageUrl}   // 待機画像をそのままポスターに使う
  controls
  playsInline
  preload="metadata"
/>
```

`poster` に待機画像を使うことで、**動画に差し替わった瞬間に見た目が飛ばない**（同じアバターが静止したまま、再生すると喋り出す）。

### 4.2 署名付き URL の扱い

- `audioUrl` / `videoUrl` は **R2 の署名付き URL（有効期限 1時間）**。ポーリングやタイムライン取得のたびに発行し直される
- **フロントで URL をキャッシュしない。** 期限切れの URL を握り続けないよう、TanStack Query のキャッシュ時間を 30分以下にする
- 長時間開きっぱなしのページで再生に失敗したら、再取得してから再生する

### 4.3 VOICEVOX のクレジット表記

**音声が再生される画面には必ず表記を出す**（例: `VOICEVOX:ずんだもん`）。

- 表記は `personas.voicevox_credit` から取得する（[04 §2.3](./04-data-model.md)）
- **ハードコードしない。** 話者を追加・変更したときの表記忘れを構造的に防ぐ

## 5. アバター表現

### 5.1 【v1】静止画 + 動画

```
待機時 : <img src={persona.avatarImageUrl} />     ← Hedra に渡すのと同じ画像
生成後 : <video src={roast.videoUrl} poster={同じ画像} />
```

**これだけ。** WebGL も Canvas も使わない。

### 5.2 なぜ Live2D をやめたか

| 観点 | Live2D | 動画生成 |
|---|---|---|
| 口の動き | リップシンクを自前で実装 | **音声から自動生成される** |
| 表情 | 表情ファイル + モーションファイルを制作 | **文脈に応じて自動で付く** |
| アセット制作 | `.moc3` / `.motion3.json` / `.exp3.json` の制作が必要 | **イラスト 1枚** |
| フロント実装 | PixiJS + `pixi-live2d-display` + Cubism Core（未経験領域） | `<video>` タグ |
| ライセンス | 事業規模による条件確認が必要 | 不要 |

**動画生成が Live2D の役割を上位互換で引き継いだ。** Q8 で映像を採用した時点で、Live2D は「同じことを、より多くの実装コストで、より低い表現力で行う手段」になった。

【将来】リアルタイム性が欲しくなったら、Live2D ではなく **Hedra Live Avatars**（$0.05/分、サブ 100ms）を検討する。同じ `AvatarVideoGenerator` の周辺に収まる。

### 5.3 `emotion` の使い道

Live2D をやめても、バックエンドが返す `emotion` は捨てない。

| 用途 | 実装 |
|---|---|
| 待機画像の切り替え | ペルソナごとに 3〜7枚の表情差分 PNG を用意し、`emotion` で選ぶ（**P1**。v1 は 1枚でも成立する） |
| 吹き出しの色調 | `ANGRY` は赤み、`WORRIED` は寒色、など CSS クラスの出し分け（**P0**、実装は数行） |
| Hedra へのテキストプロンプト | Character-3 は画像 + 音声 + **テキストプロンプト**を同時に扱う。`emotion` を演技指示として渡せる可能性がある（**P1**、P0 の検証で余力があれば試す） |

最後の項は、**バックエンドの構造化出力がそのまま映像の演出パラメータになる**という筋の良い流れなので、動くなら採用したい。

## 6. 状態管理

| 状態 | 手段 | 理由 |
|---|---|---|
| 目標一覧・詳細・タイムライン | TanStack Query | サーバ状態。キャッシュと再検証を任せる |
| **煽りジョブの進行状況** | TanStack Query（`refetchInterval`） | §3.2 |
| 進捗投稿 | TanStack Query `useMutation` | 送信中の無効化と、成功時のポーリング開始 |
| 怒りゲージ | TanStack Query | サーバが真。アニメーションは CSS transition で足りる |
| フォームの入力値 | `useState` | |

**Zustand を入れない。** v1 の UI 状態は画面ローカルで足り、状態管理ライブラリを 1つ学ぶコストに見合わない。

### 進捗投稿の流れ

```ts
// features/roast/SubmitProgressForm.tsx（骨子）
const mutation = useMutation({
  mutationFn: (input) => api.post(`/goals/${goalId}/progress`, input, {
    headers: { 'Idempotency-Key': crypto.randomUUID() },
  }),
  onSuccess: (res) => {
    // 202 Accepted。テキストは既に来ているので即座に表示する。
    setRoastId(res.roast.id);        // → useRoastPolling が動き出す
    if (res.roast.status === 'DEGRADED') {
      // コスト上限などでテキスト確定。ポーリングは走らない（pollAfterMs が null）
    }
  },
  onError: (e) => {
    // 429 → 「今日はもう煽ってもらえない」専用 UI（エラーらしく見せない）
  },
});
```

**429（レート制限）はエラー画面にしない。** 「今日のノルマは達成した、明日また来い」というアバターの台詞として見せる。

**`DEGRADED` もエラーにしない。** 「今日はもう動画は出ない」と一文添えるだけで、テキストの煽りは通常どおり表示する（[03 §1.1](./03-api-design.md)）。

## 7. アクセシビリティ

| 項目 | 対応 |
|---|---|
| **情報の完全性** | **動画が届かなくても情報は完全**。煽りの内容は常にテキストで併記される。動画は同じ内容の別表現でしかない |
| 自動再生 | しない（§4.1）。`prefers-reduced-motion` の環境でも動画は勝手に動かない |
| スクリーンリーダー | 煽り本文は `role="status"` `aria-live="polite"`。段階が進むたびに読み上げが連発しないよう、テキスト確定時に一度だけ通知する |
| 動画要素 | `<video>` に `aria-label` を付け、本文は別途テキストで提供する |
| キーボード操作 | 進捗投稿・リアクション・再生を全てキーボードで実行可能に |
| コントラスト | WCAG AA（4.5:1）。煽りテキストは特に可読性を優先 |
| 色だけに依存しない | 怒りゲージは色 + 数値 + テキストラベル。ジョブ状態も色 + 文言 |

> **「動画はテキストの上位表現であり、情報の担い手ではない」**という設計が、そのままアクセシビリティ要件を満たしている。段階表示は体験設計であると同時に、**最速の成果物が最も可搬な形式（テキスト）である**という意味で堅牢な設計でもある。
